# 企业 IM 渠道配置与联调手册

本手册对应 `docs/proposals/enterprise-im.md`，记录各渠道的配置步骤、所需权限、上线顺序和真实环境验证方法。当前可配置的渠道：**企业微信、飞书（单聊、群聊 @ Bot）、钉钉（单聊、群聊 @ Bot）**；三个渠道都支持 SOP 主动通知，写操作通过“网页确认”在平台确认后执行（企业微信另可选自动执行）。数据保留见第 9 节，升级与回退见第 2 节和第 10 节，最终测试记录见 [testing/im-final-test-record.md](testing/im-final-test-record.md)。

## 1. 平台侧前置条件

| 配置 | 说明 |
| --- | --- |
| `AGENTFLOW_PUBLIC_URL` | 用户从 IM 打开绑定页时使用的公开地址，必须是 `http(s)://host` |
| `AGENTFLOW_CREDENTIAL_KEYS` | `kid:base64(32字节)[,kid:base64(32字节)]`，第一把为当前写入密钥。所有副本配置相同的值。未配置时，已有的旧明文 Secret 仍可读取，保存新 Secret 返回 `503 credential_key_missing` |
| `AGENTFLOW_BOT_WORKERS_ENABLED` | 默认 `true`。维护窗口设为 `false`：对话接收、通知发送和数据保留清理都不启动，Bot 配置写接口返回 `503 bot_maintenance` |
| `AGENTFLOW_BOT_BODY_RETENTION_DAYS` | 默认 `90`。已结束的对话、通知、网页确认草稿的正文，以及 Bot 轮次的原生 CLI 日志，在结束这么多天后清除。`0` 表示不清除 |
| `AGENTFLOW_BOT_RECORD_RETENTION_DAYS` | 默认 `180`。已结束的记录本身在这么多天后删除。`0` 表示不删除；小于正文保留期时按正文保留期处理 |

**Compose 部署**（`./start.sh`、`./start.sh dev`、`scripts/install.sh`）：`scripts/configure.sh` 会在 `.env` 中生成 `AGENTFLOW_CREDENTIAL_KEYS`，旧的 `.env` 缺少这一项时也会自动补上；`compose.yaml` 会把它、`AGENTFLOW_PUBLIC_URL`（未设置时使用 `LOOPFORGE_PUBLIC_URL`）和 `AGENTFLOW_BOT_WORKERS_ENABLED` 传给平台容器。**`.env` 里的密钥要和数据库备份一起保管**，密钥丢失后已保存的 Secret 无法解密，只能重新填写。确认生效：平台启动日志中有 `bot credential keyring current_kid=...`；如果日志显示 `AGENTFLOW_CREDENTIAL_KEYS is not set`，说明容器没有拿到这个变量。

生成一把密钥：

```bash
echo "k$(date +%Y%m):$(openssl rand -base64 32)"
```

凭据运维子命令（不启动服务，只输出计数和 kid，不输出 Secret）：

```bash
agentflow -credential-action status
agentflow -credential-action reencrypt   # 可重复执行
```

轮换密钥：把新密钥放在列表第一位，保留旧密钥，重启所有副本后执行 `reencrypt`；`status` 显示旧 kid 计数为 0 后，再从列表中移除旧密钥。

## 2. 升级维护窗口

1. 备份数据库和当前二进制。
2. **停止全部旧版本副本。** 旧版本不认识 `AGENTFLOW_BOT_WORKERS_ENABLED`，不能依赖它暂停。
3. 以 `AGENTFLOW_BOT_WORKERS_ENABLED=false` 启动一个新版本实例。启动时的增量 DDL 会补齐新列、索引和 `bot_native_sessions` 表。
4. 执行 `migrations/036_enterprise_im_channels.sql`：
   - 第 1 段检查所有新列 `present = 1`；
   - 第 2 段列出会共用接收占位的重复启用配置，先逐一处理（停用或删除重复项）；
   - 第 3、4 段回填物理列和交互的项目快照，可重复执行；
   - 第 5 段记录各渠道配置数和未回填数，`not_backfilled` 必须为 0。
5. 执行 `migrations/037_bot_binding_ownership.sql`：第 1、2 段列出多配置共用和孤立的企微绑定，第 3 段回填唯一归属，第 4 段列出历史 Bot 原生会话（`legacy_unmapped`，只供核查，不删除）。
6. 配置 `AGENTFLOW_CREDENTIAL_KEYS`，执行 `agentflow -credential-action reencrypt`，再用 `status` 确认 `plaintext=0`。
7. **确认数据保留设置。** 开启 worker 后的第一轮清理会立刻处理升级前的历史数据：默认清除 90 天前已结束记录的正文，删除 180 天前已结束的记录，包括企业微信已有的对话记录和发送记录。需要保留更久，先在 `.env` 设置第 9 节的两个变量（或设为 `0` 暂不清理），再进行下一步。数据库备份是唯一的恢复途径。
8. 以 `AGENTFLOW_BOT_WORKERS_ENABLED=true` 重启全部新版本副本。先验证企微，再依次启用飞书、钉钉和主动通知。启动日志出现 `bot retention: …` 一行，列出本轮清理的数量；没有可清理的数据时不输出。

未执行 036 的配置（`config_version = 0`）不会建立接收连接，启动日志会提示数量。

阶段 C 之后的版本（G、H 等）没有新的手动脚本：启动时的增量 DDL 补齐 `bot_pending_drafts` 表和新增列。从任一预发版本（阶段 B 到 G）升级到最终版本，只需停旧副本、启动新版本，并按第 7 步确认保留设置。

**数据库版本**：036/037 已在 MySQL 8.4.13（默认 `sql_mode` 含 `ONLY_FULL_GROUP_BY`）和 MariaDB 10.11 上各连续执行两次，结果一致。标识比较统一用 `BINARY`，避免 `information_schema` 与业务表排序规则不同时报 1267。

**回退**：完整的回退矩阵见第 10 节。执行第 6 步（`reencrypt`）之后，库里的 Secret 是 `lf1:` 密文，旧版本会把密文当作 Secret 使用，企微连接无法鉴权。旧版本仍能启动并读出配置，但它不认识租约 epoch，会与新版本按两套协议争抢连接。因此回退必须：停止全部新版本副本 → 恢复第 1 步的备份 → 启动旧版本。维护窗口结束后新产生的对话和配置需要按停机时间段人工核对。预发演练结果见 [R1 验收记录](testing/im-r1-acceptance.md#3-预发升级与回退演练)。

## 3. 企业微信

配置方式与升级前相同。变化：

- 新建的企微 Bot 默认“只读查询”；已有 Bot 保持“自动执行”。可在第①步“执行权限”中切换。
- 阶段 G 新增“网页确认”：需要写平台数据时，Bot 不直接执行，而是回复操作摘要和确认链接（`/bot-approve.html#draft=…`，30 分钟内有效），见第 8.3 节。
- 流式回复失败后的补发，只在确认未发出（流式不可用、请求未写出、平台明确拒绝）时进行一次；已写出但未收到回执的，记录为“送达待核对”，在记录页“确认已收到”或“再次发送”。

## 4. 飞书（企业自建应用）

### 4.1 开放平台应用配置

1. 在飞书开放平台创建**企业自建应用**，记下 App ID（`cli_` 开头）和 App Secret。
2. 添加应用能力：**机器人**。
3. 事件与回调 → 订阅方式选择**使用长连接接收事件**，添加事件 `im.message.receive_v1`（接收消息）。要在通知卡片上直接审批，在“回调配置”中同样选择长连接，并添加回调 `card.action.trigger`（卡片回传交互），见第 8.5 节。
4. 权限管理中开通下表权限，创建版本并发布，可用范围设为试点成员。

| 权限（以开放平台权限列表的显示名称为准） | 用途 | 是否必需 |
| --- | --- | --- |
| 读取用户发给机器人的单聊消息 | 接收私聊消息事件 | 必需 |
| 以应用的身份发消息 | 原消息回复（Message Reply）；阶段 G 的主动通知（向绑定成员的 open_id 发单聊消息）也用这项权限 | 必需 |
| 获取企业信息 | 企业确认页展示企业名称和 tenant_key，与事件中的候选值对照 | 可选 |
| 获取群组中用户@机器人消息 | 群聊中 @ Bot 提问（2026-11-20 起） | 用群聊时必需 |
| 获取群组中所有消息 | 群里不 @ 机器人、直接引用节点问题回复（第 8.8 节） | 可选 |

**一般不需要开通“获取群组中所有消息”。** 平台只处理 @ 了机器人的群消息（按事件里 `mentions` 的 `mentioned_type=bot` 判断，旧事件没有这个字段时有任何 @ 即处理），唯一的例外是引用本群里机器人发出、仍待回答的节点问题的回复。不开通时，群成员引用问题回复要同时 @ 机器人；开通后可以不 @，但机器人会收到群里的全部消息，其余消息仍然丢弃并计入“忽略的群消息”。

**最小权限即前两项。** “获取企业信息”只影响确认页的辅助展示：未开通时，确认页显示查询失败原因，企业确认仍按“首个可信事件发现 → 管理员确认”完成。权限的精确名称和 scope 标识以应用后台为准，联调时在本表补记实际值。

### 4.2 平台配置

1. 项目 → 机器人 → 添加 Bot，渠道选择“飞书”，填写名称、App ID、App Secret，开启“启用此 Bot”和“启用对话”。保存时平台会用 App ID / Secret 获取 tenant_access_token 校验凭据，失败则不保存。
2. 进入第②步“企业确认”。此时状态为“企业待确认”。
3. 让一名试点成员在飞书里给机器人发一条单聊消息。机器人回复“机器人正在完成企业确认，请稍后重发消息。”，确认页出现候选企业标识（并显示平台查询结果是否一致）。
4. Bot 管理员点击“确认企业”。状态变为“企业已确认”，之后只处理该企业的消息。确认不会断开连接。
5. 如果出现“企业冲突”（收到了两个不同企业的消息），核实应用发布范围后点击“重新发现”。

飞书 Bot 的“执行权限”可选“只读查询”（默认）或“网页确认”。只读时，写请求会提示到平台页面操作，模型的写草稿不会执行，外部 MCP 写调用和工作区工具被拒绝。网页确认时，创建需求、派发或启动 SOP 等写操作先生成确认卡片（飞书）或确认链接（钉钉），发送者本人确认后才执行，见第 8.3 节。飞书、钉钉不提供“自动执行”。

**回答模型**：第①步“回答模型（CodeBuddy）”决定 Bot 回答对话和生成完成汇报用的模型，新建时即可选择，默认是平台默认模型，之后可随时更换。

**群聊**：把机器人拉进群后，成员 @ 机器人提问即可，不 @ 的群消息不处理（连接状态里计入“忽略的群消息”），引用节点问题的回复除外（第 8.8 节）。每个群一个会话上下文，群成员共享历史；每条消息按发言人自己绑定的平台账号和项目权限执行，没有绑定的成员会收到绑定链接（只有本人发回确认码才能完成绑定）。写操作的确认卡片发在群里，但只有发起人本人能确认，结果回复在群里。从群里启动的 SOP，失败、等待处理和完成时会发回这个群（第 8.6 节）；群里也可以一起澄清需求（第 8.7 节）。

### 4.3 用户绑定

1. 未绑定成员发消息后收到绑定链接（15 分钟有效）。有效链接存在时，再发消息会提示查看上一条链接；主动发送“绑定账号”可换新链接，每分钟最多一次，10 分钟最多三次。企业微信以 Markdown 链接展示；飞书和钉钉为纯文本消息，链接单独占一行，避免聊天客户端把后面的括号或文字识别进链接。
2. 打开链接并登录平台，页面显示渠道、机器人、项目和脱敏后的飞书发送者，确认后得到 `/bind <确认码>`。
3. 在**同一个飞书机器人的单聊**中发送该指令。绑定按机器人配置隔离：同一个人在另一个飞书机器人里需要重新绑定。
4. 绑定成功后重新发送问题。发送 `/unbind` 或在个人配置中解除绑定。

### 4.4 送达与重试

- 回复使用 Message Reply，并把持久化的发送 key 作为 `uuid`。飞书对相同 `uuid` 一小时内去重。
- 平台未返回结果时，在首次发送后 55 分钟内用同一 key 自动重试（5 秒、30 秒、2 分钟，之后每 2 分钟），超过窗口转为“送达待核对”。
- 明确未发出（连接失败、限流、令牌失效）最多自动重试 3 次，耗尽后为“回复失败”。
- 平台明确拒绝（例如原消息已撤回）直接为“回复失败”。

### 4.5 入站确认与故障恢复

- 收到事件后，平台在 2.5 秒内完成入库并回执。数据库慢或不可用时，到时直接回执失败（500），由飞书重投；重投的同一条消息按业务消息 ID 去重，只产生一条交互、只运行一次模型。
- 长连接断开后，接收服务自动重连；已在执行的回复走开放平台 HTTP 接口，不受长连接影响。
- 接收进程崩溃后，其他副本在 45 秒连接租约到期后接管：执行中的任务回复“上一轮处理已中断……”，不重跑模型；已生成未发送的回复只发送一次；发送中的回复用同一 `uuid` 重试，用户只收到一条。
- 以上场景的多进程故障测试：`internal/botinteraction/feishu_fault_mysql_test.go`，需要一个专用空库：

```bash
AGENTFLOW_BOT_FAULT_TEST_MYSQL_DSN='user:pass@tcp(127.0.0.1:3306)/bot_fault?parseTime=true' \
  go test -count=1 -run '^TestFeishuFaultMySQL$' -v -timeout 15m ./internal/botinteraction
```

## 4A. 钉钉（企业内部应用）

### 4A.1 开发者后台配置

1. 在钉钉开发者后台创建**企业内部应用**，记下 Client ID（原 AppKey）和 Client Secret（原 AppSecret）。
2. 添加应用能力：**机器人**。消息接收模式选择 **Stream 模式**（不需要公网回调地址）。
3. 发布应用，可用范围设为试点成员。
4. 记下企业的 **CorpId**（`ding` 开头，开发者后台或管理后台的企业信息里可以看到）。

原会话回复使用每条消息自带的 sessionWebhook，不需要额外的接口权限。阶段 G 的主动通知和过期回复补发调用 `POST /v1.0/robot/oToMessages/batchSend`（机器人批量发送单聊消息，`robotCode` 用 Client ID），需要在权限管理中开通“企业内机器人发送消息”相关权限。权限和字段的精确名称以开发者后台为准，联调时补记实际值；未开通时，试发会显示钉钉返回的错误码，接收人不会被保存。

### 4A.2 平台配置

1. 项目 → 通道管理 → 添加通道，渠道选“钉钉”，填写名称、Client ID、Client Secret 和**企业 CorpId**，开启“启用此 Bot”和“启用对话”。保存时平台用 Client ID / Secret 获取 accessToken 校验凭据，失败则不保存。
2. 第②步“企业确认”显示“企业待确认”。与飞书不同，**钉钉不需要手动点确认**：首条单聊消息的企业（`chatbotCorpId`）与填写的 CorpId 一致时自动确认，这条消息也会正常处理。确认人记为填写 CorpId 的管理员。
3. 不一致时状态变为“企业冲突”，之后的消息只回复“正在完成企业确认”的提示，不处理业务。核实后在第①步改正 CorpId 并保存，或点“重新发现”。企业确认后 CorpId 不能再改，更换企业请新建配置。

绑定流程和执行权限（只读查询或网页确认）与飞书相同（第 4.2、4.3 节）。发送者身份使用 `senderStaffId`；事件缺少它时丢弃并记录 `missing_staff_id`。发送者企业与机器人企业不一致的消息丢弃（`sender_corp_mismatch`）。

### 4A.3 连接与送达

- **连接**：平台自行实现 Stream 连接层，只用官方 SDK 的帧和事件数据结构（原因见 `scripts/im-sdk-probe/README.md`）。每 60 秒发一次 WebSocket ping，70 秒内没有任何数据就断开重连；收到服务端 `disconnect` 立即重连；重连由接收服务按 1 秒起的退避执行，每次重新读取凭据。
- **入站确认**：消息入库后回执 200；数据库慢或不可用时，2.5 秒内回执 500，由钉钉重投，重投按 `msgId` 去重。
- **会话回复**：sessionWebhook 只接受 `https://oapi.dingtalk.com/robot/sendBySession`，禁止重定向；以密文保存，绑定到这条交互，回复成功或过期后清除。
- **过期**：发送时离 `sessionWebhookExpiredTime` 不足 10 秒，记为“回复失败 · 会话回复授权已过期”，回复内容保留在记录页，不能在原会话再次发送。
- **重试**：明确未发出（连接失败、限流 130101、HTTP 429）最多重试 3 次。钉钉会话回复没有幂等键，结果未知（超时、5xx、系统繁忙 -1）直接记为“送达待核对”，不自动重发，由管理员在记录页确认或再次发送。

多进程故障测试 `internal/botinteraction/dingtalk_fault_mysql_test.go`（专用空库）：

```bash
AGENTFLOW_BOT_FAULT_TEST_MYSQL_DSN='user:pass@tcp(127.0.0.1:3306)/bot_fault_dt?parseTime=true' \
  go test -count=1 -run '^TestDingTalkFaultMySQL$' -v -timeout 15m ./internal/botinteraction
```

## 5. 记录页人工处理

| 状态 | 可用操作 |
| --- | --- |
| 送达待核对（`reply_unknown`） | 确认已收到；再次发送（新 key，对方可能收到重复消息） |
| 回复失败（`reply_failed`） | 再次发送；会话回复授权过期的不能在原会话再次发送。钉钉另有“改用主动单聊发送”，见第 8.2 节 |
| 机器人已删除 | 可确认已收到，再次发送返回 `bot_deleted` |
| 通知送达待核对（`send_unknown`） | 发送记录中“确认已收到”（记为人工确认）或“再次发送”（新的一代和新 key） |

停用 Bot 时，已生成未发送的回复暂存，重新启用后发送；正在执行的任务取消；发送中的记录转为“送达待核对”。

## 7. 行为变更：Bot 直接采用自然语言回答

**变更**：Bot 对话（企业微信和飞书，只读和自动执行两种模式）在模型正常结束、没有调用终态工具时，直接采用模型输出的自然语言作为回复。

**原因**：终态工具 `submit_assistant_reply` 只接受写草稿，不带草稿的提交会被拒绝。升级前，Bot 回答纯查询类问题时会重跑终态步骤两次，最后以“助手未提交回复”失败。用户收到“本次处理未完成”，模型白跑三次。在未改动的基线代码上复现：同一输入运行 3 次模型后失败。

**采用条件**（全部满足才采用）：

| 条件 | 不满足时 |
| --- | --- |
| 本次 CLI 运行成功退出 | 按原规则重跑终态步骤或失败 |
| 输出是纯文本，不含助手协议 JSON | 重跑终态步骤（协议 JSON 代表写草稿尝试，即使解析时草稿被过滤也不采用） |
| 不是“我先查一下”这类只有进度的文本（与网页助手同一判定） | 重跑终态步骤 |
| 输出非空 | 重跑终态步骤，三次仍无结果则失败 |

**不变的部分**：写操作仍然只能通过草稿或平台工具网关执行，只读 Bot 的写草稿不执行；回复里的个人凭据照常脱敏；重跑终态步骤时不会重新查询。

**影响范围**：只影响 Bot 对话入口 `generateBotReply`，网页助手、SOP 节点和通知汇报都不受影响。新老企微 Bot 和飞书 Bot 都适用。

**剩余风险**：模型输出了含义空泛的文字（例如“结果已准备好”），这段文字会原样发给用户，不再重试。这和网页助手的行为一致。

**测试**：`internal/httpapi/bot_natural_reply_test.go` 覆盖 9 种情况（只读和自动执行各自的首轮采用、只有进度、空输出、带草稿的协议 JSON、不带草稿的协议 JSON、CLI 失败、三次都无结果、凭据脱敏），另有基线对照，结果见 [R1 验收记录](testing/im-r1-acceptance.md#4-行为变更测试自然语言回答)。

## 8. 阶段 G：主动通知、过期回复补发与网页确认

### 8.1 飞书、钉钉的 SOP 通知

SOP 的完成（`succeeded`）、失败（`failed`）和待处理（`waiting`）通知，以 Bot 单聊消息发给一名**通知接收人**。只启用通知、关闭“启用对话”的配置也能发送。

1. 接收人必须先在该 Bot 的单聊里完成账号绑定（第 4.3 节）。
2. 企业确认后，配置页第③步“通知接收人”点“刷新成员列表”，列出本 Bot 已绑定的成员。
3. 选中成员后点“试发并保存”：平台先向他发一条试发消息，**平台确认送达后**才保存，并在该成员的绑定上记录 `target_verified_at`。试发失败或结果未知时不保存，页面显示原因。
4. 接收人解绑或重新绑定时，验证随之清除；之后的通知记为“会话不可用”，需要重新试发。每次发送前都会重新读取绑定和项目权限。
5. 切换接收人时，如果原接收人还有待发通知，页面会让管理员选择：改发到新接收人，或取消这些通知。两种选择都写在发送记录里。从聊天发起的运行发回原会话的消息不受影响，仍发到原来的群聊或单聊。

送达规则：

| 渠道 | 接口 | 幂等 | 结果未知时 |
| --- | --- | --- | --- |
| 飞书 | `POST /open-apis/im/v1/messages?receive_id_type=open_id`，发送 key 作为 `uuid` | 同一 `uuid` 一小时内去重 | 55 分钟内用同一 key 自动重试 |
| 钉钉 | `POST /v1.0/robot/oToMessages/batchSend` | 无 | 记为“送达待核对”，不自动重发 |

发送前先把发送 key、代数和数据库时间写入投递记录，再调用接口；进程在调用中途退出时，下一次领取能知道“可能已发出”，按上表处理。消息正文是纯文本：企微用的 Markdown 标题、加粗和链接会转成文字，链接单独一行。钉钉返回的 `invalidStaffIdList` 记为“会话不可用”，`flowControlledStaffIdList` 和 429 稍后重试。

更换 Secret 时，App ID / Client ID 不能修改，平台先用新 Secret 校验同一应用，校验通过后接收人的验证继续有效。

### 8.2 钉钉过期回复改用主动单聊

会话 Webhook 过期导致的回复失败（“回复失败 · 会话回复授权已过期”），在对话记录里可以改用主动单聊，把已保存的回复发给原发送者：

- 原发送者已经通过主动发送试发时，显示“改用主动单聊发送”；否则显示“试发给原发送者”，试发成功后再改用。试发不改变通知接收人。
- 服务端在事务内重新校验：回复仍是 `reply_failed / route_expired`、Bot 启用且开启对话、原发送者的绑定仍属于同一平台账号并通过了试发；HTTP 层另外复核项目权限。校验不通过返回 `409 push_target_unverified`。
- 通过后作为新的一代、使用新 key 发送，记录操作人、原因和“主动单聊”路由。钉钉没有幂等，结果未知时同样停在“送达待核对”。

### 8.3 网页确认（企业微信、飞书、钉钉）

“执行权限”选“网页确认”后：

1. 查询直接回答。需要写平台数据时，模型只提交草稿；平台冻结草稿（随机 ID、参数哈希、30 分钟有效），回复操作摘要和“在平台确认这些操作”链接。
2. 只有聊天发送者绑定的平台账号能打开链接。确认时重新检查：Bot 仍启用对话并处于网页确认模式、聊天账号的绑定未变、该账号仍有项目执行权限、草稿未过期、参数未被修改。任一项不满足，草稿作废并说明原因。
3. 确认在一条加锁语句里把草稿从“等待确认”改为“执行中”，重复点击或在另一个标签页确认，只返回当前状态，不会再执行。执行沿用网页助手的预检：有依赖警告的草稿不执行。
4. 执行中进程退出的草稿，10 分钟后显示“执行中断，待核对”，平台不会自动重新执行，请在平台核对结果。
5. 解绑、删除 Bot、关闭对话或改为其他执行权限时，等待确认的草稿全部作废。

**飞书的确认卡片。** 飞书 Bot 回复写操作时直接发一张卡片：上方是 Bot 的说明，下面列出操作清单；只新建一个需求时，卡片里有 SOP 下拉框（第一项“项目默认 SOP（名称）”，其后与确认页相同的 SOP 列表，最多 60 个），选择立即保存；按钮为“确认执行”“确认并启动 SOP”（有新需求时出现）“取消”和“在平台确认”（确认页会预选卡片里选的 SOP）。点按钮与在确认页确认走同一套检查和状态迁移，只有发起人本人能用，其他人点击只弹出提示“只有发起人可以确认这份操作”。

点击后卡片立即更新：按钮和下拉框被一行状态取代（例如“已提交「确认并启动 SOP」，正在执行，结果会回复在会话里”），无法再次点击；执行结果作为对这张卡片的回复，发在发起请求的会话里——群里发起就回在群里，单聊发起就回在单聊。通知卡片（通过、重试、返工等）同样在点击后隐藏按钮，结果以单聊发给点击者；钉钉模板通过 `show_*` 变量隐藏按钮、`status` 显示状态。卡片回调需要第 4.1 节的 `card.action.trigger`。钉钉仍是文字说明加确认链接。

**企业微信的确认卡片**（2026-11-20 起，Bot 需启用对话）。回复的文字（摘要和“在平台确认这些操作”链接）之后，机器人在同一会话再发一张卡片。企业微信卡片的下拉框和多个按钮不能放在同一张卡上，所以新建一个需求时，卡片是三个下拉框加一个“提交”按钮：“仓库”（项目里有仓库时出现）、“SOP”和“提交后”（确认执行 / 确认并启动 SOP / 取消，不执行）。每个下拉框最多 10 个选项，第一项是项目默认、当前选中的一定在列；没列全时卡片标题下方提示到平台确认。其他写操作是按钮卡片（确认执行、取消，附“在平台确认”跳转）。只有发起人的提交有效，其他人提交时机器人在会话里回复“只有发起人可以确认这份操作”；所选仓库或 SOP 不是本项目可选的，整份不执行。提交后卡片在回调时限内变为灰色的已处理状态，下拉框锁定；执行结果发在发起请求的会话里。

业务写入接口本身没有幂等键；“只执行一次”由状态机保证，不依赖写入接口去重。飞书、钉钉同样可以选“网页确认”（2026-11-20 起）：机制与企业微信相同，确认链接在纯文本消息中单独占一行；不提供“自动执行”。

**新需求的 SOP。** 草稿里每个新建需求后面写明将绑定的 SOP：用户在聊天里点名了 SOP 时，模型查到后写进草稿；没点名时按项目默认 SOP（与在平台新建需求的规则相同）。确认页为每个新需求提供 SOP 下拉框，与平台新建需求表单一致：第一项是“项目默认 SOP（名称）”，其后是本项目 SOP、共享 SOP 和通用模板（“通用 · ”开头，已归档的不列出），可以更换，并可勾选“创建后立即启动这个 SOP”。模型点名了 SOP 时默认选中该 SOP，改回“项目默认”后需求按项目默认绑定。只接受页面列出的 SOP；选了其他项目的 SOP 时整份草稿不执行。聊天摘要里未点名的写成“SOP：项目默认 · 名称”。启动结果写在执行结果里（“已启动：SOP 名称（运行编号）”或“未启动：原因”），需求已创建但启动失败时，可在平台手动启动。

**新需求的仓库。** 项目里有代码仓库时，摘要同样写明新需求将绑定的仓库：用户点名了仓库时，模型查到后写进草稿；没点名时按项目默认仓库（摘要写“仓库：项目默认 · 名称”；项目没设默认仓库时写“仓库：不绑定”）。飞书确认卡片在 SOP 下拉框上方多一个“仓库”下拉框（第一项“项目默认仓库（名称）”，其后是本项目的仓库），选择立即保存，只有发起人能选；确认页每个新需求也有“仓库”下拉框，并预选卡片里选的仓库。只接受本项目的仓库，选了其他项目的仓库时整份草稿不执行。执行结果写明实际绑定的仓库和 SOP。

### 8.4 升级

阶段 G 没有需要手动执行的迁移脚本。第 8.6、8.7 节（2026-11-20 追加）同样由启动时的增量 DDL 补齐：新表 `bot_chat_origins`、`bot_clarify_sessions`（utf8mb4），新列 `notification_deliveries.origin`、`bot_interactions.reply_to`。新版本启动时的增量 DDL 会补齐 `notification_deliveries` 的发送 key、代数、开始时间、平台消息 ID 和人工确认列，`bot_user_bindings.target_verified_at`、`bot_interactions.send_route`，并新建 `bot_pending_drafts`（utf8mb4）。回退到阶段 F 的版本时，这些列和表保留不用；回退前请先处理“执行中”的网页确认草稿。第 8.8 节不新增表和列。

逐项真实环境验收见 [阶段 G 验收记录](testing/im-stage-g-acceptance.md)。

### 8.5 通知卡片：在飞书、钉钉里直接审批

Bot **启用对话**时，节点**待人工确认**和**执行失败**的通知以带按钮的卡片发给通知接收人，按钮与企业微信卡片相同：通过、重试、返工、手动通过、继续、不重试（按节点当前状态出现）。完成类通知仍是文字。只开通知、不开对话的 Bot 收不到点击，继续发文字通知。

点击后：

1. 平台在回调时限内记录这次点击并回应（飞书弹出提示，钉钉在卡片状态栏显示“已收到”），然后按企业微信卡片的同一套规则处理：点击者必须已绑定平台账号并有项目权限，节点仍停在通知时的状态和轮次，按钮对应的操作仍然可用。
2. 只有通知接收人本人的点击会被执行；转发或他人点击记为“已过期或已处理”。发到群里的卡片（第 8.6 节）例外：群里任何绑定了平台账号、有项目执行权限的成员都能点。
3. 处理结果以单聊消息发给点击者，例如“「人工确认」操作已完成：确认通过，继续流程”。再次点击同一张卡片会提示已处理。

**飞书**：不需要额外配置，按第 4.1 节添加 `card.action.trigger` 回调（长连接）即可。卡片使用消息卡片 JSON 1.0，按钮值包含操作和投递编号。

**钉钉**：需要在开发者后台 → 卡片平台建一个互动卡片模板，发布后把模板 ID 填到 Bot 配置第①步的“互动卡片模板 ID”。不填时继续发文字通知。另需开通“互动卡片实例写权限”。模板约定：

| 变量 | 类型 | 内容 |
| --- | --- | --- |
| `title` | 文本 | 如“待人工确认：登录优化” |
| `content` | Markdown | 原因、待处理事项、需求、节点、SOP、返工目标 |
| `detail_url` | 文本 | 运行详情页地址，可用于“查看详情”跳转按钮 |
| `status` | 文本 | 初始为空；点击后平台回写“已收到，处理结果会以消息发给你” |
| `show_approve`、`show_retry`、`show_reject`、`show_pass`、`show_resume`、`show_decline` | 布尔 | 该按钮当前是否可用，用于按钮的显示条件 |
| `text_approve` 等 | 文本 | 平台建议的按钮文字，可选使用 |

六个按钮的点击事件设为**回传请求**，回传参数 `{"action": "approve"}`（其余按钮分别为 `retry`、`reject`、`pass`、`resume`、`decline`）。平台以 `callbackType=STREAM` 创建卡片，点击经现有 Stream 连接回传（主题 `/v1.0/card/instances/callback`），投放场域为机器人单聊（`IM_ROBOT`，`robotCode` 用 Client ID）；发到群里的卡片投放到群（`dtv1.card//IM_GROUP.<openConversationId>`，`imGroupOpenDeliverModel.robotCode` 用 Client ID）。卡片实例 ID 为“投递编号.发送 key 前 12 位”，再次发送会生成新卡片。模板变量名和权限名称以卡片平台、开发者后台为准，联调时补记实际值。

### 8.6 从聊天发起的运行，进展回到发起的会话

在飞书、钉钉、企业微信里确认“确认并启动 SOP”、派发或启动已有需求，或在聊天澄清后点“保存并启动 SOP”时，平台记下这个运行来自哪个 Bot、哪个会话、谁发起。之后这个运行的关键事件自动发回这个会话，**不需要在 SOP 或节点上配置通知 Bot**：

| 事件 | 发到会话里的内容 |
| --- | --- |
| 节点失败 | 卡片：需求、SOP、节点、失败原因，按钮“重试”“手动通过”（脚本节点）和“查看详情” |
| 节点等待人工处理 | 卡片：按钮“通过”“重试”“返工”等，按节点当前状态出现 |
| 节点需要补充信息 | 节点的问题和回答方式，可以直接在会话里回答（第 8.8 节） |
| SOP 完成 | 文字：SOP 已完成，附运行详情链接 |
| SOP 失败（没有节点失败时） | 文字：失败原因；已经有节点失败卡片时不重复发 |

规则：

1. 群里发起的发到这个群；单聊发起的发给发起人。一个运行只发回发起它的那个会话，不会发到别的群。
2. 群里的卡片，群里任何绑定了平台账号、有项目执行权限的成员都能点；操作按点击人自己的账号执行，结果回复在群里并写明操作人。点击后卡片显示“某某 已提交「重试」”，按钮消失，其他人不能再点。没绑定或只读成员点击只弹出提示，卡片不变。
3. 卡片需要 Bot 启用对话（点击要经长连接回来）；钉钉还需要第 8.5 节的卡片模板，没填时发文字。群消息使用飞书按群 `chat_id` 发消息、钉钉的机器人群消息接口（`/v1.0/robot/groupMessages/send`，`openConversationId` 为会话 ID）。钉钉需开通“企业内机器人发送群聊消息”相应权限，权限名称以开发者后台为准。
4. 如果 SOP 自己也配置了同一个 Bot、同一个接收人的节点提醒，同一事件只发一次。
5. 企业微信通过 Bot 的长连接发回（不经过通知会话列表），需要 Bot 启用对话；没启用时记录为“会话不可用”。群里的卡片同样可由任何绑定成员点击，点击后卡片更新为处理结果。
6. 这些消息在“通知记录”里可以看到，接收方显示为“发起的群聊”或“发起人（单聊）”。群消息不需要试发校验；单聊发给发起人时只要求他仍绑定在这个 Bot 上并有项目权限。

运行开始后最初几秒的事件也能找到会话：从聊天启动时，启动的会话随运行一起保存，运行的第一个事件就按它投递。只有从聊天启动的那次运行会发回会话：同一个需求之后在平台上启动的运行、只在聊天里创建而在平台上启动的需求，都不会发到聊天里；子 SOP 的运行也不单独发。

### 8.7 在聊天里澄清需求

飞书、钉钉、企业微信的单聊或群聊里都可以澄清需求（企业微信需 Bot 启用对话）。澄清用的是平台的需求澄清（读需求、代码和原单，提出问题），只是问题和回答都在聊天里进行。

**开始**：发“澄清 LOOP-7”（群里要 @机器人）。需求可以写编号（`LOOP-7`、`#7`、TAPD 编号）或完整标题；写“澄清这个需求”时，取这个会话里最近创建或启动的需求。一个会话同时只澄清一个需求，一个需求同时只在一个会话里澄清。机器人回复“已开始澄清……”，AI 分析通常需要几分钟，不受聊天回复 2 分钟的限制。

**问题**：每轮分析完成后，机器人在这个会话里主动发出问题，编号 Q1、Q2……（飞书是卡片，带“提交回答，进入下一轮”“结束澄清”按钮；企业微信先发问题文字，再发带同样按钮的卡片；钉钉是文字）。

**怎么算回答**：

| 顺序 | 规则 | 结果 |
| --- | --- | --- |
| ① | 回复（引用）澄清问题（飞书按被引用的消息判断；企业微信的引用只带文字，按引用内容里的需求编号和“第 n 轮澄清”判断） | 一定算回答；只有一个问题时记到 Q1，否则按 ②④⑤ 确定是哪一题 |
| ② | 以编号开头：“Q2：只要手机号”“2. 不需要”“第3题：……”，可以分行一次回答多题 | 记到对应问题 |
| ③ | 指令：结束澄清、继续澄清、下一轮、澄清进度、保存澄清、保存并启动、是、不是 | 按指令执行，不算回答 |
| ④ | 以上都不是（群聊） | 用便宜的模型判断是哪个问题的回答还是闲聊，把握不低于 0.75 时照办；闲聊交给机器人正常回答，不计入澄清 |
| ⑤ | 模型拿不准 | 不记录；机器人问发言人“这是对 Q2 的回答吗？”。飞书、企业微信附“是，记为 Q2”“不是”按钮（也可以回复“是”“不是”），钉钉回复“是”或“不是”。只认发言人本人 |

单聊里每条消息都算回答：没写编号时，只有一个问题或只剩一个问题未答就记到那一题，否则记为补充说明。每条回答都记下回答人，交给 AI 时写成“Q1 …
- 张三：……”，几个人的回答不一致时，AI 会在下一轮列出矛盾点再问。

**进入下一轮**：所有问题都有回答时自动开始；有人点“提交回答，进入下一轮”或发“下一轮”；或最后一条回答后 3 分钟没有新回答。30 分钟没有新回答时澄清暂停，发“继续澄清”恢复（会重新发出当前问题）。分析失败时发“下一轮”重试。

**谁能参与**：回答问题和进入下一轮——群里所有绑定了平台账号、有项目执行权限的成员；没绑定的成员 @ 机器人时收到绑定链接，他的话不计入。保存澄清结果、结束澄清——只有需求负责人（未指定负责人时为项目 Owner）、发起澄清的人和项目维护者，其他人点按钮只弹出提示。

**结论与保存**：AI 认为信息足够时，机器人发出“澄清结论”（飞书、企业微信卡片带“保存澄清结果”“保存并启动 SOP”“结束澄清”）。结论**不会自动写入需求**，在需求的澄清记录里可以看到这轮分析，状态仍是“澄清中”。有权限的人保存后：结论追加到需求描述，状态变为“已澄清”；来自 TAPD、工蜂的需求同时写回原单评论（失败时说明原因，可在平台需求详情里重试）。同一份结论只保存一次，重复点击提示已保存。执行权限为“只读查询”的 Bot 不能在聊天里保存（按钮和文字命令都按保存时的最新配置判断），提示到平台需求详情里保存，需求、原单和 SOP 都不变。“保存并启动 SOP”在保存后按点击人的账号启动需求的 SOP，运行的进展按第 8.6 节发回这个会话。还想补充时，直接说补充内容（群里需引用结论卡片）再发“下一轮”。

**与平台的关系**：每轮的问题会同步到平台需求的澄清面板；平台上正在澄清的需求不能在聊天里开始澄清。服务重启打断的分析会在约 12 分钟后自动重跑这一轮。澄清会话、回答和来源记录按第 9 节的保留期清理。

### 8.8 节点向会话提问

SOP 的任意 Agent 节点缺信息时，会提交“需要人工确认”并写明要人补充什么（`submit_gate_result` 的 `human` 决定和 `actionRequired`）。节点随后停在“等待人工确认”。对从聊天发起的运行，平台把这个问题发回发起的会话（第 8.6 节）：标题“节点需要补充信息”，带需求、SOP、节点、问题和回答方式。各渠道的形式：

| 渠道 | 问题消息 | 怎么回答 |
| --- | --- | --- |
| 飞书 | 卡片，下方是答案输入框和“提交答案”按钮 | 在卡片里填写后提交；也可以用下面的文字方式 |
| 钉钉 | 填了卡片模板时为卡片（没有按钮），否则为文字 | 文字方式 |
| 企业微信 | 文字消息（模板卡片没有输入框） | 文字方式；引用这条消息回复最方便 |

问题卡片上不再有“通过”“重试”：节点要的是答案，不补充直接放行或不带答案重跑，请到平台运行详情里操作。卡片提交后显示“某某 已提交答案：…”，输入框消失，不能再提交。

文字方式：

- 群里：@ 机器人发“回答：你的答案”。飞书、企业微信也可以直接引用问题消息回复，不用加“回答：”。飞书默认只推送 @ 机器人的群消息，引用回复时也要 @ 机器人；应用开通了“获取群组中所有消息”（第 4.1 节）时可以不 @。钉钉不提供引用信息，只能用“回答：”。
- 企业微信的问题消息带有“问题引用”标识，机器人用它定位原运行、节点和尝试次数。引用旧版通知或引用内容缺少有效标识时，机器人会列出待答问题，请用户发送“回答 序号：你的答案”确认。
- 单聊：发“回答：你的答案”，或引用问题消息回复。
- 同一个会话有几个问题没回答时，机器人列出编号，用“回答 2：…”选择。

答案提交给**同一个运行的同一个节点**：等同于平台上“补充信息，重跑当前节点”。答案作为人工补充上下文交给这个节点，节点按 SOP 继续执行，不会新建运行。群里的回复写明回答人；运行记录里有“飞书回答节点问题，平台账号：…”和答案原文。

规则：

1. IM 和平台页面处理的是同一个待答节点。谁先提交，另一边再提交都会被拒绝，提示“这个问题已经回答过，或节点已结束”。节点已结束、运行已结束或已取消时同样不能提交。
2. 回答按发言人自己绑定的平台账号执行。没有绑定的成员会收到绑定链接，项目只读成员和非项目成员会被拒绝，答案都不会提交。
3. 只有发到这个会话的问题才能在这个会话里回答：群里的问题只能在这个群回答，单聊的问题只能由发起人回答。
4. 不以“回答：”开头、也没有引用问题消息的消息，按普通对话处理。
5. 飞书卡片的输入框留空提交时，卡片提示“请先填写答案”，不会提交。

## 9. 数据保留（阶段 H）

### 9.1 规则

每个运行 Bot worker 的进程每小时清理一次，每批 1000 条，每类每轮最多 10 批，时间从记录**实际结束**算起：

| 数据 | 正文保留期（默认 90 天）到期后 | 记录保留期（默认 180 天）到期后 |
| --- | --- | --- |
| 对话交互（`bot_interactions`），状态为已回复、回复失败、已取消 | 清空消息、引用、回复和会话回复路由，记录 `body_purged_at`；记录页显示“正文已按保留期清理”，不能再次发送 | 删除 |
| 通知发送记录（`notification_deliveries`），状态为已发送、失败、已取消、已过期、会话不可用 | 清空渲染后的正文和 AI 汇报请求，`content_source=purged`，不能重试 | 删除 |
| 网页确认草稿（`bot_pending_drafts`），状态为已执行、失败、已过期、已取消 | 清空草稿、摘要和执行结果 | 删除 |
| Bot 轮次的原生 CLI 日志 | 按映射删除日志文件，见 9.2 | 日志已删除或确认不存在的映射被删除 |
| 聊天澄清会话（`bot_clarify_sessions`），状态为已保存、已结束 | 清空问题、回答和结论 | 删除 |
| 运行和需求的聊天来源（`bot_chat_origins`） | — | 按创建时间删除，之后该运行不再回发会话 |

**不清理的数据**：排队中、执行中、待发送、发送中、送达待核对（`reply_unknown`、`send_unknown`）、待授权、网页确认的“执行中”和“执行中断，待核对”。这些记录保留到有人处理为止。等待确认的草稿过期后先改为“已过期”，再按上表处理。账号绑定、Bot 配置、会话映射（`bot_conversations`）和连接状态不在清理范围内。

“实际结束”的取法：对话交互和草稿用最后更新时间；通知发送记录没有结束时间列，要求创建时间、最后一次尝试时间和发送时间都早于期限，最近重试过的记录不会被提前清理。清理正文时不改动更新时间，所以记录保留期仍从结束时算起。

### 9.2 原生 CLI 日志

Bot 轮次在用户共用的 CLI HOME（`AGENTFLOW_ASSISTANT_SESSION_DIR/<用户 ID>/home`）中运行，同一目录里还有其他来源的日志。清理只处理同时满足以下条件的文件：

- 对应的 `bot_native_sessions` 映射已结束（完成、失败、中断），且结束时间早于正文保留期；
- 文件名等于映射记录的请求 session ID 或 CLI 报告的 session ID：CodeBuddy 在 `.codebuddy/projects`、`.codebuddy/sessions` 下，Claude Code 在 `.claude/projects` 下，Codex 按线程 ID 匹配 `.codex/sessions/**/rollout-*-<线程 ID>.jsonl`，并从 `codex-threads.json` 删除对应条目；
- 位于该映射所属用户自己的 CLI HOME 内。不跟随符号链接；日志目录经过符号链接指向 HOME 之外时整棵跳过；
- 同一个 session 仍被其他未结束或未到期的映射使用时，本轮跳过。

每条映射记录结果：`removed`（附删除的相对路径）、`missing`（没找到文件）、`error`（下一轮重试）、`unsupported`（该 CLI 的日志位置未登记，例如 OpenCode、Kimi Code，保留供人工核查）。查看统计：

```sql
SELECT engine, cleanup_status, COUNT(*) FROM bot_native_sessions GROUP BY engine, cleanup_status;
SELECT id, user_id, requested_session_id, native_session_id, cleanup_detail FROM bot_native_sessions WHERE cleanup_status IN ('error', 'unsupported');
```

多个 API 副本部署时，`AGENTFLOW_ASSISTANT_SESSION_DIR` 需要是共享存储；否则没有执行该轮的副本找不到文件，会记为 `missing`，日志留在原副本上。状态为 `started` 的映射（进程在运行中退出）保留追踪状态，不自动清理。

**升级前的历史日志**没有映射，清理永远不会触碰它们。`migrations/037_bot_binding_ownership.sql` 第 4 段在升级时列出 `legacy_unmapped` 交互清单，请在开启 worker 之前导出保存：记录保留期到期后这些交互会被删除，清单就无法再生成。按清单人工核查后再决定是否删除对应日志。

### 9.3 调整与暂停

- 改保留期：修改 `.env` 中的两个变量后重启。缩短保留期会在下一轮立即生效；延长保留期不能恢复已清理的数据。
- 暂停清理：两个变量都设为 `0`，或者维护期间设置 `AGENTFLOW_BOT_WORKERS_ENABLED=false`（同时停止收发）。
- 清理结果：日志 `bot retention: interaction bodies=… interactions=… notification bodies=… notifications=… drafts expired=… draft bodies=… drafts=… native mappings=… native logs handled=…`；失败时输出 `bot retention: cleanup failed`，下一小时重试。

## 10. 回退

| 回退目标 | 做法 | 数据影响 |
| --- | --- | --- |
| 最终版本 → 阶段 B 到 G 的预发版本 | 停止全部新版本副本，启动目标版本。新增列和表保留不用 | 停止数据保留清理。以下按各阶段代码推断：回到阶段 F 及更早：排队中的飞书、钉钉主动通知会被取消（“该渠道的主动通知尚未开放”），网页确认链接失效（`/bot-approve.html` 不存在），等待确认的草稿不再执行。回到阶段 E 及更早：钉钉配置不再建立连接 |
| 最终版本 → 未接入 IM 的版本，未执行凭据重新加密 | 停止全部新版本副本，启动旧版本 | 旧版本能读出配置并使用明文 Secret；但它不认识租约 epoch，必须先停全部新副本。新增列和表保留不用。旧版本不认识渠道字段，飞书、钉钉配置会被当作企微配置读取（按代码推断，未演练），回退前先停用这些配置 |
| 最终版本 → 未接入 IM 的版本，已执行凭据重新加密 | **只能**停止全部新版本副本 → 恢复升级前的备份 → 启动旧版本 | 维护窗口之后新产生的对话、配置和通知需要按停机时间段人工核对；已被数据保留清理删除的记录随备份恢复 |
