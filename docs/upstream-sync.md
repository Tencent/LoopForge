# 内部与开源版本的长期对齐

建议目标是**同一份平台核心、两套部署与连接适配**。不要长期维护两份各自重写的 engine、repo、runner 或 web；也不要把整个内部仓库反复覆盖到开源仓库。当前改造保留上游目录、Go module、核心数据结构和环境变量名称，就是为后续逐步收敛做准备。

## 推荐的长期结构

| 范围 | 维护位置 | 变更流向 |
| --- | --- | --- |
| 引擎、SOP、审批、任务、产物、执行协议、通用 UI | 公共核心 | 开源优先，内部消费 |
| GitHub、公共登录、公开模型配置 | 公共适配器 | 开源维护，内部可复用 |
| 内部 SSO、内部系统连接、组织策略 | 内部适配器 | 内部维护，通过接口接入核心 |
| 域名、账号、Token、部署脚本、业务项目和生产 seed | 私有部署仓库/配置 | 永不导出 |
| LoopForge Local | `local/` 本地工作流与测试，`docs/local/` 使用文档 | 用契约对齐平台，保持独立安装 |

最终让内部版本直接依赖公共核心的明确版本或 Git 提交，内部补充适配器。可以是同仓核心加私有发行仓，也可以是稳定 Go package/module 依赖；先隔离接口，再决定是否拆 module。现在不宜为了仓库布局重写成熟业务代码。

## 过渡期：可审计的双向移植

1. `upstream.json` 固定本次内部 master 的完整 SHA 和源文件哈希，`upstream-overrides.json` 列明开源修改与删除。`scripts/check-upstream.py` 校验公共适配之外的代码没有悄悄漂移。
2. 定期在内部网络创建同步分支，比较“已记录 master → 新 master”。按提交移植共享功能，保留开源适配；用三方合并处理冲突，禁止直接复制覆盖。脚本只检查/报告，不自动向 GitHub 推送。
3. 通用 bug 优先在公共核心修复，附回归测试。内部修复急需先上线时，下一步必须建立对应开源移植单，提交记录 `Upstream-Commit`；反向记录 `Public-Commit` 或公开 PR 链接。
4. 开源 PR 先通过公共 CI，再移植内部适用的提交。保留原作者署名与 PR 链接，使用 `git cherry-pick -x` 或等效来源记录，避免把社区贡献重新写一份。
5. 每次同步更新来源 SHA、适配清单、数据库迁移与执行协议兼容矩阵。不要仅更新 SHA 却遗漏代码，也不要将尚未移植的提交标成已同步。

移植时需要保留完整依赖链，不只挑表面修复提交。内部和开源身份/权限、追踪器、配置及 schema 不同，冲突必须由对应适配测试判定，不能自动选一边。

## 一个功能从 PR 到两边上线

社区 PR → 公共核心评审和回归 → 公共发布候选 → 内部适配 CI → 内部灰度 → 发布。

内部需求 → 判断共享功能还是内部适配 → 共享部分提公共 PR，内部部分留私有适配 → 两套 CI → 分别发布。

给移植单维护 `待判断 / 待移植 / 验证中 / 已发布 / 不适用（有原因）`。公共 PR 不应强制等待内部上线，内部发布也不应反向改写已经发布的公共版本。同步负责人定期检查未闭环的条目即可，不需要两边锁步发布。

## CI 与发布契约

- 共享：Go 单元/集成测试、MySQL schema、Web 语法、API 契约、runner 握手与产物格式。
- 公共：干净环境安装、密码登录、GitHub/MCP 权限绑定、公开内容检查、中英与亮暗主题、CLI 安装回归。
- 内部：组织登录、内部连接器、部署拓扑、内部项目与历史数据迁移。
- 兼容：给破坏性 API / runner 协议变更明确版本窗口；迁移先加后切，旧 runner 保留过渡期，不能假设服务与所有执行机器同时更新。
- 发布：平台与 CLI 分开版本、分开发包；公共发布必须能在无内网、无内部账号和无已有数据库的环境完成安装。

当前提供的是可运行的过渡版本和差异清单。建议下一阶段优先把公共登录、远端仓库/PR、模型目录、通知和组织策略收敛为正式接口，再把已验证的公共改造按功能带回内部 master。这样两边会逐步减少差异，而不是每次同步累积新分叉。


## 本轮应回移的通用修复

- Runner 取消后停止监听已完成的 context；输出读取完成后仅由一个 goroutine 执行 `cmd.Wait`，提前退出时也回收子进程。真实进程取消、退出码和 managed CLI 清理回归已通过重复执行及竞态检测。预览归档测试改为等待异步工作区清理完成后再关闭数据库，避免测试结束与 finalizer 竞争。
- Main Bot 独立选择 CodeBuddy / Codex / Claude，按当前操作人绑定凭据；会话保留执行器，原生工具限制和平台审批保持一致。
- MCP Shell 前置代码仅注入真正的 Shell，避免把 Codex 的 `-c` 配置参数、Python 的 `-c` 源码破坏。真实 CLI 本地网关测试已覆盖。
- 本地执行与 Git 命令限制仓库向上查找，防止任务工作区意外使用平台源码仓库；Codex 工具 Shell 也保留这条边界。
- SOP 运行条件按每个角色的实际执行器检查凭据；执行器协议回归和 E2E 清理范围隔离适合两边共用。
- 自定义 MCP 的组合 ID 超出数据库列长时稳定截断并附加完整作用域摘要；保留原有短 ID，避免长名称无法保存。
- 模型、审批和引用菜单随可视窗口及滚动位置调整，避免小屏和短窗口遮挡。
