# Changelog

Platform releases use `vX.Y.Z` tags and publish `ghcr.io/tencent/loopforge`. LoopForge Local packages use `local-vX.Y.Z` tags and are published by manually running the `release-local` workflow.

## Unreleased

### Platform

- **Breaking:** the `local` sandbox type is removed and native sandboxes only carry environment variables. A native sandbox runs on whichever machine executes the work (a user's execution machine, a cloud runner or the platform host) with that machine's own toolchains; environment install scripts, `$PREFIX` and install PATH entries are gone, and settings such as `JAVA_HOME` go into the sandbox's environment variables. SOPs and conversation workspaces can use Docker or native sandboxes; the default sandbox is `generic-docker`, and `AGENTFLOW_LOCAL_SANDBOX` is removed. A local row that was not migrated reads as native; a run frozen with a local sandbox asks to be started again with a native one.
- Native SOP checkouts use a private repository cache on each execution machine. The platform or Runner refreshes the bare repository with the checkout's Git credentials and copies Git objects into the worktree. This reuses the network fetch and leaves each worktree and checkpoint independent. Docker sandboxes keep direct clones. Conversation workspaces start empty and the agent clones using the current speaker's credentials. Runner 0.12.0 supports cached SOP checkouts.
- Users can choose a preferred sandbox kind in 设置 → AI 助手 → 对话工作区. The preference (`workspaceDriver` in `/api/assistant/preferences`) prioritizes that kind among compatible environments. A task can require another toolchain, and a fixed conversation environment takes precedence. The workbench groups sandboxes by kind, and the header displays the current workspace's sandbox type icon and ID beside the execution machine. Startup AutoMigrate and migration 041 both add the preference column.
- **Breaking:** a docker sandbox now carries its own Dockerfile, and the 环境资产 page becomes 「沙箱管理」 without type tabs: the sandbox editor holds the Dockerfile and its build-context files for docker, and only environment variables for native. Dockerfiles and install scripts are no longer separate assets. `/api/dockerfiles`, `/api/environments`, the `dockerfiles_*` / `environments_*` assistant and MCP tools and the `dockerfiles` / `environments` bootstrap fields are removed; `PUT /api/sandboxes` takes `dockerfile {content, files}` in place of `dockerfileId`, and rejects `driver: local`. Before starting the upgraded platform, apply `migrations/041_native_sandbox_inline_assets.sql` to existing databases with `./start.sh migrate-sandboxes` for Compose or directly for external MySQL. It copies each referenced Dockerfile into its sandbox, turns one that no sandbox used into a sandbox of its own, turns local sandboxes into native ones, copies ordinary variables from referenced environments, drops install scripts and `PATH` from native sandbox variables, and moves SOPs that used the old default to `generic-docker`, and drops the `dockerfiles` and `environments` tables. Docker images are reused.

### enterprise IM channels (Feishu and DingTalk chats, proactive notifications, data retention)

- Runs started from a Feishu or DingTalk chat (confirm and start, dispatch, or save-and-start after a chat clarification) report back to that conversation without any SOP notification binding: a failed or waiting node arrives as an action card, the end of the run as a short message. Group runs report to the group, where any bound project member can use the card buttons as themselves; the card then names who acted and locks. Feishu sends group messages by `chat_id`, DingTalk through the robot group message API and `IM_GROUP` cards. The starting conversation is stored with the run when it is created; a later run of the same requirement started on the platform is not sent to the chat.
- A node that needs supplementary information (a `human` decision with `actionRequired`) sends its question to the chat the run was started from. Answering in that chat (“回答：…”, or a reply to the question in Feishu and WeCom) retries the same node of the same run with the answer as human context, like “补充信息，重跑当前节点” on the platform. On Feishu the question card has an answer input and a “提交答案” button instead of approve and retry; WeCom template cards have no text input, so WeCom gets the question as a text message to quote. IM and the platform act on the same waiting node: an answered question, an ended node or a cancelled run refuses further answers, and answers run as the sender’s bound account with the project permission checked. WeCom quotes identify the original node attempt by the question message's delivery reference. Older or incomplete quotes without a usable reference prompt the user to select a question by number. In Feishu groups a reply to the question needs no @ when the application has the “read all group messages” permission. See `docs/im-channels.md` section 8.8.
- WeCom Bots with chat enabled match Feishu: write confirmations come with a card (a multiple-choice card with repository, SOP and operation drop-downs for a new requirement, otherwise buttons), runs started from a WeCom chat report back to it over the long connection, and requirements can be clarified in WeCom chats with button cards.
- Requirements can be clarified in Feishu and DingTalk chats: “澄清 LOOP-7” runs the platform clarification in the background and posts each round's numbered questions into the conversation. In groups any bound member may answer; numbered answers and quotes of the question card count, other messages are judged by a small model, and when it is unsure the speaker is asked to confirm. The next round starts when all questions are answered, on request, or three minutes after the last answer. A conclusion is written into the requirement (and back to TAPD or 工蜂) only when the responsible person, the starter or a project maintainer saves it, once; a read-only Bot refuses to save. New tables `bot_chat_origins` and `bot_clarify_sessions` and the columns `notification_deliveries.origin` and `bot_interactions.reply_to` are added by the startup DDL. See `docs/im-channels.md` sections 8.6 and 8.7.
- Feishu and DingTalk notifications of waiting or failed nodes are action cards when the Bot has chat enabled: approve, retry, rework or pass directly in the chat, with the same checks as WeCom cards; the result comes back as a private message. Feishu needs the `card.action.trigger` callback on the long connection; DingTalk needs an interactive card template ID in the Bot settings (empty keeps text notifications).
- Feishu and DingTalk Bots answer in group chats when @-mentioned (Feishu needs the “read @-bot messages in groups” permission); other group messages are ignored. Each group has its own shared context and every message runs as the sender's bound account.
- Feishu write confirmations are a card with “确认执行 / 确认并启动 SOP / 取消” buttons instead of a bare link; only the requester can use them and the result arrives as a private message. The Bot form labels the model field “回答模型” and keeps “默认” selectable.
- Requirements created from chat show the repository and the SOP they will be bound to (the project defaults unless named in the chat); the Feishu confirmation card and the confirmation page let the user choose another repository and SOP of the project and start it right after creation.
- **Chat Bot data now has a retention period.** An hourly cleanup removes the text of finished conversation turns, notification deliveries and web-confirmation drafts, and the native CLI logs of Bot turns, 90 days after they finished, and deletes the finished records after 180 days. This also applies to existing WeCom conversation and notification records on the first start after upgrading. Records still waiting for someone (in progress, ready to send, delivery unknown) are kept. Set `AGENTFLOW_BOT_BODY_RETENTION_DAYS` and `AGENTFLOW_BOT_RECORD_RETENTION_DAYS` (0 keeps forever) before enabling the Bot workers if you need longer. Records whose text was removed show “正文已按保留期清理” and cannot be sent again. See `docs/im-channels.md` sections 9 and 10.
- Feishu and DingTalk Bots send SOP notifications (completed, failed, waiting) as private messages to one member who bound an account in a private chat with the Bot; notification-only configurations (chat disabled) work too. Saving the recipient first sends a trial message and only a confirmed delivery is accepted; unbinding clears it. Feishu unknown outcomes are retried with the same uuid for 55 minutes, DingTalk ones stop at 送达待核对, where managers can confirm receipt or send again. Switching the recipient with queued notifications asks whether to move or cancel them. See `docs/im-channels.md` section 8.
- A DingTalk reply whose session webhook expired can be sent to the original sender as a proactive private message from the record page, after that member passed a trial send.
- WeCom Bots gain the 网页确认 write mode: writes come back as a summary and a confirmation link, the bound user confirms on the platform page, and a draft runs at most once. Feishu and DingTalk Bots can use the same mode (they cannot write automatically), so requirements can be created and SOPs dispatched or started from a private chat after a confirmation on the platform page.
- DingTalk enterprise internal applications can be added as Bots over Stream mode: private text chats, account binding and read-only queries, replies through each message's session webhook. The administrator enters the enterprise CorpId; the first matching message confirms it automatically, another enterprise stops processing as a conflict. The Stream connection is implemented by the platform (only data types of `open-dingtalk/dingtalk-stream-sdk-go` v0.9.1 are used) because the SDK's client can crash the process after a heartbeat timeout. Session webhooks are stored encrypted and cleared when used or expired; replies whose webhook expired stay on the record page as 会话回复授权已过期. See `docs/im-channels.md` section 4A.

- Feishu self-built applications can be added as Bots: private text chats, account binding and read-only project queries over the official long connection (`larksuite/oapi-sdk-go` v3.13.0). The first message from a new application records its enterprise; a Bot manager confirms it before any request is processed, and messages from other enterprises are dropped. See `docs/im-channels.md`.
- **New WeCom Bots default to read-only.** A Bot created from now on answers queries but does not write; writes are refused with a pointer to the platform page. Existing WeCom Bots keep automatic execution. Managers choose the mode under 执行权限.
- **WeCom fallback send changed.** A reply whose stream fails is sent again as a proactive message only when the stream provably did not go out (stream unavailable, request never written, or rejected by WeCom). A stream that may have been delivered but had no receipt is no longer sent twice: the record shows 送达待核对, and a manager chooses 确认已收到 or 再次发送 (a new delivery that may duplicate) on the record page.
- **Disabling a Bot keeps generated replies.** Queued and running turns are cancelled, replies already generated wait and are sent after the Bot is enabled again, and a send in progress becomes 送达待核对. Deleting a Bot cancels unsent work, moves in-flight sends to 待核对, and revokes the Bot's chat bindings.
- Bot secrets are encrypted with AES-256-GCM using `AGENTFLOW_CREDENTIAL_KEYS`. Compose installations get a generated key in `.env` (added to existing `.env` files on the next `./start.sh`), and `compose.yaml` now passes `AGENTFLOW_CREDENTIAL_KEYS`, `AGENTFLOW_PUBLIC_URL` and `AGENTFLOW_BOT_WORKERS_ENABLED` to the platform container. Back up `.env` together with the database. Existing plaintext secrets stay readable; `agentflow -credential-action status|reencrypt` reports and migrates them. Without a key, saving a new secret returns `credential_key_missing`.
- **Bot chats accept a plain natural-language answer.** Before, a Bot turn could only end through `submit_assistant_reply`, which refuses replies without drafts, so plain query answers ran the model three times and failed with 助手未提交回复. Now plain text from a successful run is the reply; protocol JSON, progress-only text, empty output and failed runs still go through the terminal retry. Writes still need drafts or the tool gateway. Applies to WeCom and Feishu Bots, not to the web assistant or SOP nodes.
- Receiving leases, send windows and retries are judged on the database clock with an epoch per owner, so a replica that lost its lease can no longer overwrite a reply or send it twice. Notification deliveries gain the state `send_unknown`.
- Upgrading needs a maintenance window: stop every old replica, start the new version once with `AGENTFLOW_BOT_WORKERS_ENABLED=false`, run `migrations/036_enterprise_im_channels.sql` and `migrations/037_bot_binding_ownership.sql`, run `-credential-action reencrypt`, then restart with workers enabled. Bots not backfilled by 036 do not receive messages.

## 0.4.2 — Conversation recovery and assisted approvals

- Existing conversations can resume after a skill installation leaves an unsupported symbolic link in their managed skill directory. The platform and Runner remove these links during asset preparation, record the cleanup in the turn activity, and report filesystem failures separately from session locks (#1261).
- In `Assisted` (「帮我批准」) mode, AI review makes the final decision. An unavailable review blocks the action. The reviewer can follow the conversation's CLI and model, use another configured CLI and model, or use a standalone API (#1216).

**Upgrading from v0.4.1.** Check out `v0.4.2` and run `./start.sh pull` for a Compose installation. The platform adds the new approval review columns on startup. For workspaces on remote execution machines, update the connected Runner from its machine card after upgrading the platform, then start a new turn in the affected conversation. See the [Runner update instructions](docs/conversation-native-cli.md).

For a direct upgrade from `v0.4.0`, follow the [GitHub credential migration instructions](docs/deployment.md#migrating-existing-github-credentials) before starting the new version.

## 0.4.1 — Git and MCP credentials, SOP orchestration and conversation workspaces

- Configure HTTPS Git credentials per host, authorize the IP addresses of self-hosted HTTPS Git servers, and distribute trusted SSH host keys to execution machines. MCP servers, market items and SOP nodes can use configured credentials.
- Use personal conversation workspaces, refresh the repository context on demand and restore a conversation's model and send preferences. Replies report the CLI and version that ran them. Conversation workspaces can recover after their Docker instance stops.
- Runners support Antigravity login and managed updates for six agent CLIs. Installations can use other supported providers for platform model features that previously required CodeBuddy.
- AI scheduled tasks can reference project assets and wait for a triggered SOP to finish. Execution history records token usage and the dashboard shows totals.
- The SOP designer's AI orchestrator runs as its own conversation surface (`surface: "sop-designer"` on `POST /api/assistant/chat` and `/api/assistant/generations`) instead of a workbench chat with a long prompt built in the browser. The server now writes the designer system prompt, the project's roles (all of them, no longer the first 40), the canvas snapshot and the SOPs the user named into each turn as data, so the transcript keeps only what the user typed. A designer turn always runs in confirm mode with read-only platform tools only: no workspace, browser or external MCP, and the model can submit nothing but one `workflows_save` draft. Its conversation is private to the author, no longer appears in the workbench history (where it used to show up with the generated prompt as its title) and cannot be continued there; `GET /api/assistant/sessions?surface=sop-designer&workflowId=…` lists it. A second message in the same orchestrator conversation no longer fails with 「共享会话已更新，请重新打开后发送」, which happened because the canvas resent a simplified history of a project-shared session. `workflows_save` drafts from any conversation now warn about duplicate node ids, edges to missing nodes, self loops and cycles before they are saved, and the 「构建静态站点」 node no longer warns that role `af-preview-builder` does not exist.
- The orchestrator panel embeds the chatbot (`/chatbot/?surface=sop-designer`) instead of its own hand-written chat. Replies render Markdown with the execution trace, a running turn can be stopped, the turn runs as a background generation, so closing the panel or reloading the page no longer loses it, and reopening a SOP shows its earlier conversation. The CLI and model choice keeps its own memory as before. Each reply's draft shows its warnings and can be put on the canvas again. The canvas and the chat talk only through `agentflow-sop-designer-*` window messages; the canvas still animates nodes and wires as the draft streams in.
- Editing a SOP in the orchestrator no longer rewrites the whole graph. On a canvas with steps the model submits `operations` (`add_node`, `update_node`, `remove_node`, `add_edge`, `remove_edge`, `update_workflow`) and the server applies them to the canvas it received, so steps, prompts, scripts, layout and the 「构建静态站点」 node the user did not mention stay exactly as they were. An operation that does not fit the canvas (an unknown node, a duplicate edge, removing a node another step rejects to) goes back to the model with the reason instead of reaching the canvas. The canvas no longer guesses intent from the wording: it no longer matches 「重新…」 or 「去掉预览」 phrases or SOP names in the message; the server lists the project's SOPs and the model reads the one the user means. A draft with a different SOP id replaces the canvas only after the user confirms.
- The orchestrator offers the model only roles a SOP save accepts: roles of this project and roles another project shares. A built-in role that belongs to no project used to be offered, and the draft then failed on save with 「角色 … 不属于当前项目且尚未共享」. `workflows_save` drafts from any conversation now warn about such a role before saving. A script longer than 400 characters reaches the model as a marker that says it is omitted, not as an empty string; the model used to report the script as empty and offer to write one, and a marker copied back into a draft is replaced by the canvas's script.
- The side browser no longer stays on a blurry frame after a scroll or drag on a page that stops changing. Scrolling switches the screencast to half-size frames and it restarts at full size once input settles, but Chromium does not always re-send a page that is not repainting; the panel now captures the page when no frame arrives within 300 ms.
- The floating page-feedback button is gone. The page-feedback API goes with it. Existing `page_feedbacks` and `page_feedback_images` tables are left in place and are no longer created for new databases.
- On macOS `/bin/bash` 3.2, a missing local image or a failed automatic mirror pull no longer aborts `./start.sh` before the official image pull.
- `./start.sh` and `./start.sh pull` time `ghcr.io` and `ghcr.nju.edu.cn`. Nanjing is used only when the ghcr.io manifest digest was verified and the mirror returned the same digest; the pull is that digest, then tagged back to the name pinned in `compose.yaml`. A missing official digest, a digest mismatch, or a failed mirror pull stays on `ghcr.io`. `MIRROR=ghcr.io` forces the upstream registry; `MIRROR=<host>` still forces that host and does not fall back. Accepting Nanjing, or setting `MIRROR`, trusts that host. The choice is not saved in `.env`. `registry-mirrors` such as `https://docker.nju.edu.cn` only accelerates Docker Hub.

**Upgrading from v0.4.0.** Stop the old API and workers and keep MySQL running. Manually apply [`036_git_http_credentials.sql`](migrations/036_git_http_credentials.sql) from this release before starting the upgraded platform or running `./start.sh pull`. Verify private repository access after the upgrade. After the rollback window, follow the [credential migration guide](docs/deployment.md#migrating-existing-github-credentials) to apply `037_retire_plain_git_token.sql`.

The Compose installer and `./start.sh pull` replay `033_generic_sop_mr_node.sql` and then `038_generic_sop_host_credentials.sql` for unmodified built-in delivery SOPs. See [Updating existing public SOPs](docs/deployment.md#updating-existing-public-sops) for manual deployments. Installations that need historical scheduling totals can backfill retained executions with the optional `039_schedule_execution_legacy_stats.sql` after meeting the prerequisites in its header.

## 0.4.0 — scheduled task history, an MR node in delivery SOPs and agent CLIs in conversation workspaces

- Scheduled tasks keep an execution history with a session mode, keep conversations per job and gain row actions (#958). AI jobs run with the key of the user who saved them and fall back to the shared key (#966).
- Requirements can be created directly and clarified in a chat (#965). Settled execution history can be force-deleted (#210).
- Conversation workspaces open by sandbox with agent-owned Git (#947), run native agent CLIs on bound execution machines (#494), can be bound to project SOP workspaces through `workspaceRunId` (#974), and install a missing CLI from the failure message (#183).
- Run workspaces can be edited while agents run (#211), and a reclaimed workspace can be restored from the run details (#968).
- Git repositories can use SSH with a personal key per host (#207).
- The assistant asks for approval before external MCP writes (#973), surfaces specific CLI failures and exports turn diagnostics (#468). The chat remembers the chosen model and approval mode.
- The runner gains CLI authentication and maintenance controls (#972).
- The home page no longer offers the one-click demo starter (#960).
- Messages queued in a conversation are kept when switching to another conversation and back (#1004).
- 「创建并去对话澄清」 sends again. The first message of the new conversation @-mentions the requirement, and the turn links that issue to the conversation while starting; the start then compared the conversation it read before linking and refused its own link with 「关联需求已更新，请重新发送」 every time. The same happened to any later message that @-mentioned an issue in a conversation without a linked issue. A turn now accepts the issue it linked itself; a conversation rebound to another issue while the turn starts is still refused.
- A conversation's 子 Agent shows the model it ran on: its row in the artifacts list reads 「已完成 · 模型 …」, the header of an opened subagent names the model next to its status, and each dispatch in 会话过程 notes 「模型 · …」 under the task it was given. The model is the one the subagent reports running on: its first line in the CLI stream is saved as an `agentModel` activity event under the dispatch, so an alias such as `lite` shows the model it resolved to. Until it reports, and for replies saved before this change, the panel falls back to the model the Agent call named (the `model` argument), else the model of the reply that dispatched it, which the subagent inherits; a dispatch still running uses the model the running reply was sent with. Activity events of an Agent call carry the new `model` field only when the call named one.
- The built-in backend, frontend and defect-fix SOPs gain a 「发起 MR」 node between 人工验收 and 交付汇总 (#717). It commits the work branch, pushes it and opens an MR/PR against the run's target branch, then records the link, branches and commit SHA in `mr-body.md`. Its command gate checks every writable repository of the run: one with commits beyond the target branch fails while it has uncommitted changes, while its checkout is off the run's work branch, or until `git ls-remote origin` shows that work branch at HEAD. A repository the run left unchanged is skipped. A second gate of the new mode `mr` has the engine look the MR up on the host with the same lookup delivery tracking uses (GitHub and Gongfeng): every writable repository whose work branch on origin carries commits beyond the target branch needs an MR from that work branch into that target branch that carries the pushed tip: an open one whose head is the tip (or whose host reports no head), or a merged one whose head is the tip. An agent that reports pass without opening an MR, opens it against the wrong branch, or leaves only an earlier merged MR on a reused work branch does not reach 交付汇总. The lookup runs as the run: on GitHub with the Git token the run pushed with (its responsible user's), falling back to the Owner of the run's own project; on Gongfeng through the run project's MCP as the responsible user. A repository bound to several projects is no longer checked as whichever project bound it first, and a failed lookup names the identity it used. A host the platform cannot query (an SSH repository, a failed lookup) goes straight to a person. `mr` gates take no commands, and the role editor keeps them when a role is saved. The gates retry once with their feedback and then wait for a person, so a run no longer succeeds with every source change left in a workspace that is reclaimed right after success. Run-scoped commands now get `AGENTFLOW_WORK_BRANCHES` (one `dir<TAB>work branch<TAB>target branch` line per writable repository) and repository-scoped commands get `AGENTFLOW_WORK_BRANCH` and `AGENTFLOW_BASE_BRANCH`; the target branch is the one frozen into the run, including a requirement's release branch and a scheduled SOP's integration branch. 交付汇总 no longer pushes or opens a PR itself. Runs without a bound repository still deliver from the task workspace. New installs get the new templates from the seed. Existing installs keep their templates until an operator runs `migrations/033_generic_sop_mr_node.sql` by hand (see docs/deployment.md); it rewrites a template only while its node graph and 交付汇总 position are the shipped original and its 交付汇总 prompt only while unedited. SOPs already adopted into a project are copies and keep their old graph. The product SOP delivers documents only and is unchanged.
- A conversation reply that is still running keeps running through a slow heartbeat. A poll, the conversation list, a follow-up message or a steer used to record it as interrupted after 45 seconds without a stored heartbeat; the process then cancelled the CLI and the next message failed with 「工作区正在使用或保存，请稍后重试」 for up to 15 minutes. Reads of a turn this process executes no longer reap it, and an unchanged heartbeat on MySQL no longer counts as a lost turn. On MySQL a heartbeat's age is measured on the database clock that stamped it, so skew between an API host and MySQL neither reaps a live turn nor keeps a dead one; whether a lease holder stopped renewing is likewise judged from `run_workspace_checkpoints.lease_renewed_at`, stamped on the database clock, not from another replica's `lease_until`. When a turn whose process died is reaped, the workspace lease it recorded is released if nothing renewed it for 45 seconds, so the next message starts at once; a lease another turn took, one still renewed on another replica, and a background save are kept. `migrations/032_assistant_generation_workspace_lease.sql` adds the three columns by hand; startup AutoMigrate adds them too.

- The platform image bundles DeepSeek Harness `@deepseek-ai/dsh@0.2.2-rc.1` next to Codex and CodeBuddy, so a DeepSeek key works in conversations and SOP roles without an install step. 0.3.8 had no `dsh` and answered a DeepSeek Harness chat with “AI 助手生成失败，请稍后重试”. The image download grows by about 180 MB. An installation without the image installs the same pinned version from the conversation: every dsh release is a prerelease requiring Node 24.9, and npm on Node 22 found no version for the bare package name.
- A conversation workspace whose image lacks the chosen CLI installs Cursor CLI and Antigravity again. The sandbox drops every capability, so the installer's `tar` running as root could not restore the archive owner (`Cannot change ownership to uid 2000`), and the turn failed with “准备 cursor 原生CLI失败”. The workspace install of DeepSeek Harness uses the pinned `@deepseek-ai/dsh@0.2.2-rc.1` with relaxed engines, as the platform install already did; the bare package name resolved to no version.
- A conversation workspace on a custom Dockerfile without Node.js, npm or Python 3 runs the CLIs bundled in the platform image (Codex, CodeBuddy, DeepSeek Harness). The platform copies its Node.js, npm and a relocatable Python 3.12 into `${LOOPFORGE_DATA_DIR}/cli/toolchain/<build>/` on first use, and a bundled CLI the first time a sandbox needs it; every sandbox mounts that directory read-only at the end of `PATH`, so tools shipped by the image still win. The platform image gains python-build-standalone (about 30 MB to download, checked against a pinned SHA-256). Other CLIs are still installed inside the sandbox, now with the mounted npm. A musl (Alpine) or foreign-architecture image, which lacks the loader the copied `node` needs, keeps its own `PATH` and installs with its package manager as before. Each platform build gets its own directory of about 200 MB plus the CLIs it copied; directories of earlier builds are not removed, so delete the other `cli/toolchain/<build>/` directories after an upgrade.
- A DeepSeek Harness reply longer than 8 KB (about 2,700 Chinese characters) is shown in full. `dsh --json` cuts every event string at 8 KiB and only its `final` event carries the whole answer, so the chat stopped mid-sentence while the saved reply was complete.
- SOP sandboxes of the published image install OpenCode, Kimi Code and Pi on first use, as they already did for Claude Code. An SOP role on one of these CLIs used to fail with `exec: <cli>: not found` (exit 127) even after a conversation installed it.
- Run logs and telemetry redact every environment variable ending in `_API_KEY`, `_TOKEN`, `_SECRET` or `_PASSWORD`. Agent CLI keys such as `DEEPSEEK_API_KEY`, and `AGENTFLOW_CLI_API_KEY` used with a custom Base URL, used to appear in clear text in the `docker exec` line of an SOP run log, readable by project members. Rotate a key that ran an SOP role before this release.
- Upgrading with `./start.sh pull` now re-applies the schema pieces gorm AutoMigrate cannot create: the `run_telemetry.adapter` and `run_logs.level` generated columns from `migrations/001_run_obs_generated_columns.sql`, and the `INSERT IGNORE` starter catalog. A data volume from an older release no longer fails with `Error 1054 Unknown column 'adapter'` the first time someone opens a run detail. The installer and the upgrade command share one script, `scripts/install-schema-extensions.sh`, and a failed step stops the command with the migration file an operator has to run by hand.
- Deleting a conversation removes its shared native root (`shared/<hash>`). It used to stay on disk, about 73 MB each because every root holds its own CLI home with the CodeBuddy plugin marketplace, so a scheduled task that replaces its previous run on every cycle grew the disk by one root per run. The daily session janitor also removes roots left behind earlier once their conversation is gone and they have not changed for a day.
- CodeBuddy no longer downloads its built-in plugin marketplaces into every conversation and workspace. Each one has its own CLI home, so each new conversation used to take about 72 MB; it now takes under 1 MB. LoopForge installs no CodeBuddy plugins, and conversations that already downloaded the marketplaces keep working.
- Native conversation roots move to `AGENTFLOW_CONVERSATION_DIR`, which `compose.yaml` sets to `${LOOPFORGE_DATA_DIR}/conversations`. They used to sit in the `platform-data` volume under `/data/assistant`, a path the host Docker daemon does not have, so opening a conversation workspace on a Compose installation failed with `mkdirat ... read-only file system`. Attachments and other per-user assistant data stay in `/data/assistant`; nothing needs moving. A customised `compose.yaml` needs the same setting. `docs/deployment.md` now spells out the upgrade steps: update the checkout, then `./start.sh pull`.
- The built-in `generic-backend` Dockerfile includes `openssh-client` again, matching the platform image, so a `generic-docker` workspace or SOP sandbox starts on the platform image instead of building `agentflow-img-*` on first use. #207 added the package to the platform image but not to the starter catalog. The installer and `./start.sh pull` run `migrations/031_generic_backend_openssh.sql`, which updates the row only while it still holds the unedited previous default.
- `docs/deployment.md` splits `migrations/` into scripts the installer already covers, scripts an upgrade must run once, and scripts that only backfill existing rows.
- The 预览/源码 switch in the chat artifact preview now matches the 30px copy and download buttons beside it (36px on narrow screens) instead of using the 48px page-level tab size.
- Requirement clarification, Bot replies, run evals and the SOP preview build list only CodeBuddy models, because they run on CodeBuddy. `POST /api/chat-clarify`, `POST /api/issues/{id}/chat-clarify` and `POST /api/runs/{id}/eval` answer 400 for a model of another CLI (such as `codex:…`) instead of switching it to the CodeBuddy default; a Codex model saved earlier in these pickers falls back to the CLI default (#228).

- Repository clone URLs no longer carry credentials. Saving a `cloneUrl` with a user name or password, such as `https://user:token@github.com/acme/app.git`, is rejected with a pointer to the Git token in personal settings; the repositories API, bootstrap payload, run, task and requirement views, and the runner task management list strip credentials from `cloneUrl` and `webUrl` of rows saved earlier; a `webUrl` with credentials is rejected on save; runner clone errors and redacted Git output mask them. `ssh://git@host/...` and `git@host:path` remotes are still accepted.

Repositories saved earlier with a token in `cloneUrl` keep cloning until they are saved again. Saving one from the studio stores the URL without the token, so first put the Git token in 个人配置, then save the repository. Until then the token also lands in each workspace's `.git/config`, where the agent can read it, so re-save such repositories soon after upgrading.

Startup AutoMigrate creates the tables and columns of migrations `028` to `035`, and the installer and `./start.sh pull` apply `031`. `030` only aligns the stored `shared` flag of `generic-docker` with what the application already reads and is optional. To add the 「发起 MR」 node to the built-in SOPs of an existing installation, run `migrations/033_generic_sop_mr_node.sql` by hand (see `docs/deployment.md`). Rotate any agent CLI key that ran an SOP role before this release.

## 0.3.8 — header sign-in hardening and a GHCR mirror option

- With `AGENTFLOW_TRUST_IDENTITY_HEADERS=true`, identity headers such as `Staffname` are ignored on requests that carry `X-Forwarded-For`, `Forwarded` or `X-Real-IP`, unless the gateway also sends `X-AgentFlow-Gateway-Secret` matching the new `AGENTFLOW_IDENTITY_HEADER_SECRET`. A client behind a pass-through reverse proxy could otherwise sign in as any account. Deployments with the option off are unaffected.
- MCP, REST and quick-access snippets copied from an HTTPS studio use `https://` endpoints, so agents no longer send their Bearer token over cleartext HTTP.
- `MIRROR=<host> ./start.sh` pulls `<host>/tencent/loopforge:<version>` and tags it back to the name pinned in `compose.yaml`. `ghcr.nju.edu.cn` is one such host. Unset `MIRROR` still pulls `ghcr.io` directly. `MIRROR=<host> ./start.sh pull` refreshes through the same host. Setting `MIRROR` trusts that host. The published image stays on GHCR, and the GitHub Release records its digest. `registry-mirrors` such as `https://docker.nju.edu.cn` only accelerates Docker Hub.
- The release workflow publishes GHCR only. It no longer copies the image to `ccr.ccs.tencentyun.com`.
- The assistant asks before handing a requirement to an SOP, does not run a rejected proposal, and no longer runs the same draft twice after a timeout.
- The side browser renders sandbox dev servers natively instead of through screencast frames.
- The workbench shows the image's short git commit in the corner.
- The AI orchestrator's canvas build animations are back, and follow the dark theme.
- The chatbot clears the missing-key notice once quick access saves a key.
- Sandbox Git cleanup keeps `index.lock` while a process holds it through a bind-mounted or hard-linked path.
- Tool messages and executor output are clipped on UTF-8 character boundaries.

Before upgrading a deployment that signs users in by header behind a proxy adding forwarding headers, set `AGENTFLOW_IDENTITY_HEADER_SECRET` and have the gateway send it in `X-AgentFlow-Gateway-Secret`; otherwise header sign-in falls back to guest after the upgrade. See `docs/deployment.md`.

No migrations are required.

## 0.3.3 — Codex and Claude Code roles in Docker sandboxes

- Codex SOP roles in Docker sandboxes run with `--sandbox danger-full-access`: the container is the isolation boundary, and Codex's own bubblewrap sandbox cannot create namespaces inside it, so every shell command, file write and `submit_gate_result` call failed.
- Claude Code SOP roles run with `--permission-mode bypassPermissions` (as CodeBuddy roles already did) instead of `dontAsk`, which denied every file write, shell command and the gate tool. Docker sandboxes set `IS_SANDBOX=1`, without which Claude Code refuses that mode as root.
- The installer labels the addresses it prints (public, LAN, this machine) and reads the public IP from the cloud provider's link-local metadata service, so a cloud host behind NAT no longer shows only its private address.
- The 0.3.0 and 0.3.1 images were republished without Claude Code.
