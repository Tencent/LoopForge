# DESIGN 阶段规则

1. 按“需求报告 → 项目规则 → 现有实现与测试 → 受影响调用链 → 方案与计划”的顺序调研；重要结论标注仓库相对路径或用户决策。
2. 方案必须说明现状、目标行为、组件或调用链变化、接口/数据/兼容性影响、备选方案取舍、未知项和非目标；证据不足时明确阻塞或采用可回退的低风险默认值。
3. 执行计划的每个任务必须是动作导向、可跟踪的工作单元，写明依赖、目标文件、具体动作和完成证据；共享文件或迁移依赖不得伪装成可并行任务。
4. 先用测试目录、配置、清单脚本和 CI 证据盘点项目已有测试层级，再把验收标准和高风险变更映射到合适层级与真实命令。项目已有 E2E 且本次修改影响其覆盖的用户旅程、路由或跨进程行为时，计划必须包含补充/更新 E2E；项目没有 E2E 时不得为了流程强行引入新框架。不得只笼统写“补单测”。
5. HTTP API 有新增、修改或删除时，执行计划必须包含从 `templates/api-docs.md` 生成 `03-code/api-docs.md` 的任务。数据模型、迁移、安全边界或发布行为变化时，说明兼容性、失败恢复和回滚方案。
6. 只产出方案与计划，不实现代码，不为通过校验而改变已确认语义。
