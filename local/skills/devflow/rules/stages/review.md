# REVIEW 阶段规则

1. 以实际 diff 为主证据，并对照需求、执行计划、变更报告及项目规则检查完成度；报告声称完成但 diff 或验证证据不支持时必须指出。
2. 检查正确性、边界与错误路径、兼容性、安全与隐私、性能与资源、并发与幂等、可维护性、代码规范和测试充分性；逐条核对验收标准是否在合适层级被覆盖，不能用单元测试替代必要的集成、契约或 E2E 证据。只报告本次变更引入或暴露的可操作问题。
3. 严重级别：P0 为安全漏洞、数据损坏或系统不可用风险；P1 为明确的功能、兼容性、稳定性或发布阻断；P2 为非阻断改进。存在 P0/P1 时结论必须为不通过，仅有 P2 或无问题才可通过。
4. 每条问题必须包含文件和尽可能精确的位置、触发条件、实际影响、证据及修复方向；无法证明的问题写为风险或待确认项，不伪装成缺陷。
5. 检查计划中每项完成证据和验收标准是否有真实对应；缺少关键实现或关键验证按 P1 处理。
6. 保持独立，只审查不修改代码、不代替 IMPLEMENT 修复，也不把纯格式偏好当成阻断问题。
7. 对照实际 diff 检查 HTTP API 变动。新增、修改或删除接口却没有生成 `03-code/api-docs.md`，或者文档与路由、请求/响应、权限、错误不一致时，按 P1 阻断；change report 错写“无接口变动”同样阻断。
