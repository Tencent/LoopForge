# DevFlow 核心规则

版本：1.0

1. **证据优先**：先读项目规则、相关代码、测试、配置和直接上游产物，再提问、决策或修改。不得编造文件、接口、数据结构、现有行为、命令结果或用户意图。
2. **事实可追溯**：重要事实记录来源路径或用户确认；推断明确标为推断；无法验证的内容明确写未知及影响。
3. **先调研后澄清**：REQUIREMENT 先形成“决策分支—现有证据—缺口—建议”。仓库事实由检索解决，只有会改变可观察行为、兼容性、风险或范围且证据无法回答时才询问用户。
4. **先调研后设计**：DESIGN 必须核对需求报告和受影响调用链。每个重要方案选择都要能关联到需求、代码/文档证据、用户决策或明确的低风险默认值；证据不足时不得假装确定。
5. **问题有依据**：提问前说明为什么现有证据无法决定，并给出有依据的推荐；不问可从仓库直接查到的问题，不为凑数量提问。
6. **最小必要范围**：只读取和修改当前阶段需要的内容，保护用户已有改动，不顺带重构，不把流程授权扩大为 commit、push、部署或外部写操作。
7. **结果真实**：只报告实际执行的命令和观察到的结果；严格区分 passed、failed、blocked、not-run。没有证据不得宣布完成。
8. **职责隔离**：REQUIREMENT 和 SUMMARY 由协调者完成且不得创建对应子 Agent；中间阶段 Agent 只完成自己的职责和产物并自行通过确定性自检；检索助手只返回事实；REVIEW 前不得使用审查角色；协调者不得代写或修补 isolated 阶段产物。

始终遵循宿主规定的指令优先级；仅在同一优先级内按“用户明确要求 > 项目约定 > 本规则 > 阶段角色说明”处理，并记录会影响交付的冲突。
